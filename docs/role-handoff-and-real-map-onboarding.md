# Передача Kivo: Ариадна, Егор, backend и реальные карты

Документ распределяет оставшуюся работу после стабилизации backend API. Он не заменяет OpenAPI,
инструкцию Intuiface или эксплуатационную документацию, а связывает их в один исполнимый процесс.

## Текущее состояние и главный пробел

Backend-логика kiosk flow реализована и протестирована: bootstrap, каталог, поиск, события,
построение маршрута, PNG overlay, QR/shared route и feedback. Проверенный OCI-образ публикуется в
GHCR. Постоянный staging/production-сервер пока не предоставлен.

В backend есть защищённый endpoint публикации уже записанной версии графа:

```text
POST /api/v1/admin/malls/{mallCode}/navigation/graphs/{versionId}/publish
```

Endpoint валидирует и атомарно активирует граф, но не загружает исходный PDF, список мест, узлы или
рёбра. Production-importer и редактор разметки пока отсутствуют. Демонстрационные данные загружаются
отдельным SQL seed и не являются форматом передачи реального объекта.

## Что должна передать Ариадна

### 1. Пакет исходных планов

Для каждого этажа требуется отдельная папка:

```text
<mall-code>/
  source/
    <floor-code>.pdf|svg|dwg
  kiosk/
    <floor-code>.png
  metadata/
    floors.xlsx
    places.xlsx
    kiosks.xlsx
    vertical-links.xlsx
  figma/
    link-or-export.txt
```

Обязательные свойства исходника:

- официальное название, версия и дата плана;
- этаж и стабильный `floorCode`, например `B1`, `L1`, `L2`;
- единицы измерения или минимум два контрольных реальных расстояния;
- границы области, которая войдёт в kiosk-карту;
- ориентация и точка отсчёта;
- подтверждение, что разрешено хранить и показывать план в киоске и мобильной странице;
- список удалённых технических, служебных и чувствительных обозначений;
- checksum переданного файла, чтобы дальнейшие версии не смешивались.

Если исходник не является финальным as-built планом, это явно записывается в metadata и запрещает
production-публикацию без повторной проверки.

### 2. Фоновая карта для киоска

На каждый этаж нужен PNG без нарисованного маршрута:

- одинаковый crop с системой координат backend;
- сохранённое соотношение сторон, без дополнительного растяжения в Intuiface;
- читаемые подписи при фактическом разрешении Player;
- прозрачность либо фон, согласованный с макетом;
- без персональных данных, служебных маршрутов и секретной инфраструктуры;
- версия файла в имени или manifest, но стабильный публичный URL после публикации;
- отдельная проверка размера файла и времени загрузки на сети киоска.

Маршрут, стрелки старта/финиша и подсветка переходов в PNG не рисуются: backend возвращает их
отдельным прозрачным overlay с теми же pixel bounds.

### 3. Таблица этажей

Для каждого этажа Ариадна передаёт:

| Поле                     | Пример               | Правило                               |
|--------------------------|----------------------|---------------------------------------|
| `floorCode`              | `L1`                 | стабильно, без локализованного текста |
| `displayOrder`           | `10`                 | порядок переключателя этажей          |
| `displayNameRu/En`       | `1 этаж` / `Floor 1` | все согласованные языки               |
| `imageFile`              | `L1.png`             | соответствует утверждённому crop      |
| `pixelWidth/Height`      | `2048/1712`          | фактический размер PNG                |
| `coordinateWidth/Height` | `10000/8358`         | система координат backend             |
| `metersPerUnit`          | `0.01`               | только после калибровки               |

### 4. Таблица мест и категорий

Для каждого публичного места нужны стабильный внешний код, категория, этаж, порядок показа,
названия и описания на всех языках. Дополнительно:

- публичная дверь/точка назначения, а не центр закрытого помещения;
- временный или постоянный статус;
- расписание, если оно влияет на доступность;
- связь события с маршрутизируемым местом;
- изображение/логотип только при наличии прав;
- явная пометка отсутствующего перевода — не подмена машинным переводом без согласования.

Изменение названия не должно менять внешний код места. Закрытое место деактивируется, а не
переиспользуется для другого арендатора без решения о миграции истории.

### 5. Состояния экранов в Figma

Помимо happy path должны быть нарисованы и подписаны:

- loading каждого запроса;
- пустой поиск и отсутствие событий;
- недоступный маршрут;
- ошибки `400`, `404`, `422`, `429`, `503`;
- network/CORS/TLS failure;
- истёкший QR/shared route;
- unavailable image/overlay;
- доступный профиль маршрута;
- multi-floor переход и переключение этажа;
- idle warning и полный reset;
- success feedback без response body.

Для каждого элемента Ариадна указывает источник данных: статический текст, переменная experience
или конкретное поле API. Макет не должен зависеть от navigation node IDs — они не выдаются наружу.

### 6. Что Ариадна не должна определять по изображению самостоятельно

Без подтверждения владельца площадки нельзя считать достоверными:

- доступность дверей и лифтов для МГН;
- режим работы проходов, лестниц и эскалаторов;
- одностороннее движение;
- запретные и эвакуационные зоны;
- реальные расстояния и ETA;
- соответствие дверей на плане фактическим входам;
- пары межэтажных площадок и уровень, на который они ведут.

Такие поля передаются как `UNVERIFIED` и блокируют production acceptance.

### Definition of Done Ариадны

- [ ] все этажи имеют утверждённые исходники, crop и PNG;
- [ ] таблицы этажей, мест, категорий, киосков и переходов заполнены;
- [ ] внешние коды стабильны и не дублируются;
- [ ] все тексты согласованы для каждого языка;
- [ ] в Figma присутствуют loading/error/empty/idle/multi-floor состояния;
- [ ] реальные ограничения подтверждены площадкой либо помечены блокером;
- [ ] пакет имеет версию, дату, владельца и changelog.

## Что должен сделать Егор в Intuiface

Подробные endpoints, POST bodies и error mapping находятся в
[`intuiface-integration.md`](intuiface-integration.md). Ниже — обязательный рабочий чек-лист.

### 1. Зафиксировать среду

- версия Composer;
- тип и версия Player;
- ОС и разрешение экрана;
- лицензия и доступность API Explorer/REST Interface Assets;
- browser engine и правила certificate trust;
- сетевой маршрут до staging backend;
- точный origin для CORS;
- наличие remote debugging и способ выгрузки логов.

### 2. Создать конфигурацию experience

Конфигурация не зашивается отдельно в каждый экран. Нужны общие переменные `baseOrigin`,
`kioskCode`, `mallCode`, `lang`, `categoryId`, `placeId`, `profile`, `routeId`, `shareId`,
`overlayUrl`, `routeUrl`, `qrImageUrl` и `correlationId`.

Для demo и staging значения должны различаться без пересборки UI. Admin credentials и share token
никогда не сохраняются в experience или аналитике.

### 3. Создать и проверить REST Interface Assets

- Bootstrap;
- Categories;
- Places;
- Place;
- Events;
- Create route;
- Get route;
- Share route;
- Feedback.

Для каждого IA Егор фиксирует method, URL template, query, headers, body, success trigger, failure
trigger и поля ответа. Требуется фактически проверить, что Player считает `201` и `204` успешными.

### 4. Реализовать экранный сценарий

1. Startup вызывает Bootstrap, затем Categories, Places и Events.
2. Язык обновляет все локализованные запросы.
3. Поиск и категория очищают несовместимый предыдущий выбор.
4. Карточка места сохраняет только публичный `placeId`.
5. Route screen показывает базовую карту и прозрачный overlay с одинаковыми bounds.
6. Multi-floor route переключает карту и overlay как единую пару.
7. Share показывает QR и локальный countdown до `expiresAt`.
8. Feedback принимает `1..5`, блокирует повторный tap после `204`.
9. Idle/reset очищает весь предыдущий пользовательский контекст и повторяет Bootstrap.

### 5. Реализовать безопасную обработку ошибок

На `Request failed` старый successful response скрывается. Пользователю показывается нейтральное
сообщение, а в support log попадают endpoint, HTTP status, стабильный `code` и `correlationId`.
Нельзя логировать share token, полный QR URL или admin credentials.

`429` учитывает `Retry-After`; `404` route/share возвращает пользователя в каталог; `422` сообщает
о невозможности маршрута; `503` предлагает повторить позже; network/CORS/TLS имеет отдельный экран
«Нет связи».

### 6. Проверить карты и overlay

- базовый PNG не растягивается независимо по осям;
- overlay располагается pixel-perfect поверх карты;
- relative URL дополняется `baseOrigin` ровно один раз;
- `Change image` обновляет remote PNG после каждого route;
- кэш не показывает предыдущий маршрут;
- на нескольких этажах не смешиваются карта и overlay разных `floorCode`;
- QR читается реальным телефоном с требуемого расстояния;
- mobile route открывается из сети посетителя, а не только из сети киоска.

### 7. Передать доказательства приёмки

Егор передаёт таблицу с Composer/Player/OS, временем теста, endpoint, ожидаемым и фактическим
результатом. Для ошибок и multi-floor flow нужны screenshot/video и correlation ID. Полный сценарий
проходится минимум десять раз после cold start и минимум десять раз после idle reset.

### Definition of Done Егора

- [ ] все Interface Assets работают через staging HTTPS;
- [ ] `201`, `204` и Problem Details проверены на целевом Player;
- [ ] карты, overlay и QR работают без ручного refresh;
- [ ] error state не показывает cached пользовательские данные;
- [ ] idle/reset полностью очищает состояние;
- [ ] STANDARD и ACCESSIBLE проверены;
- [ ] multi-floor маршрут проверен минимум на двух этажах;
- [ ] acceptance-таблица и доказательства переданы владельцу продукта.

## Пошаговый процесс разметки реальной карты

### Шаг 1. Зафиксировать геометрию этажа

Выбрать crop, сохранить его неизменным и задать `coordinateWidth=10000`. Высота вычисляется из
aspect ratio. Для исходной точки `(sourceX, sourceY)` документируется однозначное преобразование в
Kivo `(x, y)` с началом в левом верхнем углу. После утверждения графа crop менять нельзя без новой
версии карты и пересчёта всех координат.

### Шаг 2. Калибровать метры

Использовать минимум два измеренных непараллельных отрезка. Если масштаб по осям различается,
исправить экспорт; компенсировать растяжение одним `metersPerUnit` нельзя. Сохранить исходные точки,
реальную длину, вычисленный коэффициент и допустимую погрешность.

### Шаг 3. Разметить узлы

Узлы ставятся на осевой линии публичного движения:

- повороты и пересечения;
- публичные двери мест;
- позиции киосков;
- входы/выходы;
- площадки лифтов, лестниц и эскалаторов;
- точки изменения ограничения.

Нельзя ставить destination anchor в центре закрытого помещения, если посетитель должен остановиться
у двери. Узлы получают стабильные внешние коды, не зависящие от database UUID.

### Шаг 4. Разметить рёбра и geometry

Каждое ребро содержит начало, конец, длину, тип движения, направление, accessibility и при
необходимости промежуточную polyline. Двусторонний проход либо явно задаётся в обе стороны, либо
импортируется по документированному правилу. Линия не должна пересекать стены, закрытые помещения
или пустоты только потому, что это геометрически короче.

### Шаг 5. Связать этажи

Каждый вертикальный переход имеет подтверждённую пару landing nodes. Лифт, лестница и эскалатор —
разные movement types. Для эскалатора фиксируется направление; для ACCESSIBLE допускаются только
подтверждённые переходы. Одинаковое визуальное положение на двух PNG не доказывает связь.

### Шаг 6. Привязать места и киоски

Каждый активный киоск получает ровно один стартовый узел на своём этаже. Каждое публичное место
получает routable anchor у фактической точки подхода. Один общий anchor допустим для нескольких
мест только при осознанном решении, например для общей стойки.

### Шаг 7. Dry-run и экспертная проверка

Importer выдаёт errors и warnings. Errors блокируют запись/публикацию. Warnings подписывает владелец
данных. Дополнительно человек визуально проверяет наложение тестовых маршрутов на каждый этаж.

### Шаг 8. Публикация и acceptance

Новая версия сначала загружается неактивной. После проверки она публикуется атомарно. Затем
проверяются readiness, случайные маршруты, все киоски, оба профиля, multi-floor overlay и Intuiface.
Предыдущая версия и её manifest сохраняются для анализа и управляемого отката приложения.

- [ ] каждое место достижимо из каждого активного киоска;
- [ ] ACCESSIBLE подтверждён обследованием, а не только планом;
- [ ] все межэтажные переходы проверены на месте;
- [ ] overlay pixel-perfect совпадает с картой на целевом Player;
- [ ] Intuiface acceptance и idle/reset пройдены;
- [ ] нагрузочный тест, backup restore и rollback завершены;
- [ ] release image зафиксирован digest и release tag;
- [ ] назначены владельцы контента, эксплуатации и инцидентов.

## Порядок выполнения

1. Backend/DevOps поднимает staging и сообщает контракт адресов/файлов.
2. Backend утверждает import format и предоставляет validator/dry-run.
3. Ариадна передаёт versioned visual/content package.
4. Площадка подтверждает геометрию, ограничения и доступность.
5. Backend импортирует данные, исправляет технические ошибки и публикует staging graph.
6. Егор подключает Intuiface и проходит технический checklist.
7. Ариадна проводит визуальную приёмку экранов и overlay.
8. Команда проводит натурную, нагрузочную и recovery-приёмку.
9. Только после подписанного результата создаётся первый release tag и production deployment.
